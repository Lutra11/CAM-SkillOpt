## 2. 这些方法实际优化了什么

| 方法 | 改变的主要对象 | 求解时额外机制 | 反馈与选择 |
|---|---|---|---|
| Meta-Harness | 可执行的完整 harness 程序 | 由搜索得到的程序决定 | 搜索任务评分、完整历史工件、候选/Pareto 选择 |
| Self-Harness | 当前 harness 的局部可编辑入口 | 采用后的检查、恢复或运行策略 | 验证器证据、失败机制、分割回归门控 |
| MESH-Harness | 各 slot 的实现及它们的组合 | 最终冻结的组合 | 完整组合评分、共享线性代理、轨迹驱动更新池 |
| Harmony | tools / skills / logic 及适配范围 | 按任务生成并执行组合 DAG | 功能性与安全性、多目标分解搜索 |
| ActiveSaddler | 训练证据的选择策略 | 不要求额外在线课程层 | 动态模式、预期学习价值、探索/重访 |
| Procedural Graphs | 程序关系图的结构与属性 | 定位、子图、当步指导 | 训练成败对照、非下降验证、拒绝历史 |
| GraphSkillEvo | 图结构自然语言技能种群 | 由模型阅读技能；不强制执行图 | 失败驱动变异、交叉、验证集适应度 |
| FRESH | 经验图和辅助检索器 | 四类经验提示、动作前置条件 gate | 动作/修复反馈、图检索器训练 |
| RHO | 指令、技能、工具组成的目录 | 所选目录中的指令和工具 | 优化时自验证、自一致性和配对自偏好 |

这些方法解决的层次不同。课程、记忆、技能表示、程序搜索、组合选择并不是可以直接互换的部件；把它们全部加进一个框架，也不能自动成为有清晰贡献的新方法。

当前主链是执行、反思、合并、排序、技能更新与验证；环境差异由 adapter 处理，核心更新对象仍是技能内容。

在整个系统中，Trainer 组织优化，adapter 组织领域执行，模型后端提供调用，技能编辑与 gate 决定保留哪个文本产物。数据流以任务轨迹和候选技能为中心。优点是冻结模型、可读产物和环境复用；代价是观察、检查与恢复等程序行为主要由预置执行器决定。

本次文献可用于重新审视这些边界：什么应变成优化产物，什么应是固定评价设施，怎样记录候选行为与真实反馈。此处提供理解映射，不要求立即修改这些代码。

## 4. 内网可行性：推理 API 与训练依赖分开看

下表是基于现有接入记录的工程判断，**不是作者已经验证过的 GLM/Qwen 结果，也不是本次实时网关探测**。近期记录见[模型调研](../../experiments/CAM_SKILLOPT_ZGCI_EXPERIMENT_PLAN.md)与[参数及路由记录](../../experiments/ZGCI_MODEL_HUB_API.md)。

| 方法 | 仅使用现有 LLM 推理 API 可否实现主要闭环 | 需要额外确认的依赖 |
|---|---|---|
| Meta-Harness | 可以，需本地构建可读写工件的提案 Agent | GLM 代码提案能力、受控执行与接口检查 |
| Self-Harness | 可以；同模型或跨模型设置应分别标注 | 失败签名、可编辑入口、回归评价协议 |
| MESH-Harness | LLM 权重无需训练，bandit 本地运行 | 固定 embedding 编码器、池接口、线性代数 |
| Harmony | 无需训练 LLM 的主方法具有可行性 | 多目标评分、候选运行、DAG 组合与校验 |
| ActiveSaddler | 可以，课程决策主要由推理与本地状态实现 | 模式 registry、底层框架优化器及其评估成本 |
| Procedural Graphs | 可以，图操作在本地，指导/refiner 用 API | 真实执行事件、定位接口、在线指导预算 |
| GraphSkillEvo | 可以，主要是技能生成、执行和本地筛选 | 图技能解析、多个候选的运行时间 |
| FRESH | 完整原方法不能仅凭推理端点就认定可复现 | GNN 检索器训练及文本特征；规则替代属于变体 |
| RHO | LLM 权重无需训练，完整检索选择需额外资源 | embedding/DPP、自偏好校准、重跑和评审开销 |

GLM 提案、Qwen 执行是适配选择。Self-Harness、GraphSkillEvo、Procedural Graphs 等论文有同模型角色设置；改为异构角色后必须如实记录。`minimax` 在旧记录中映射到 Qwen，不能据别名就计为独立模型。GLM 的 reasoning 参数行为应使用已有角色配置及后续能力检查，不能直接照搬其他厂商模型的 effort 设置。

## 5. 需要纠正或避免的常见误读

1. Meta-Harness 原文也维护候选与 Pareto 权衡，不宜把“多目标”视为 Harmony 相对所有前作完全没有先例的特征；Harmony 的具体方法是分解式功能/安全演化及范围组织。
2. Self-Harness 的 held-out 参与接受判断，应按回归验证角色理解；最终完全隔离测试需另外安排。
3. MESH 的 bandit 选择完整组合。完整协方差不等于其预测均值显式建模任意非线性交互，也不提供组件独立因果奖励。
4. ActiveSaddler 主实现采用 LLM 估计学习价值与探索决策，不能简化成一个标准 UCB 算法。
5. Procedural Graphs 是在线软指导，GraphSkillEvo 是结构化技能；两者都不能未经说明改写成强制状态机。
6. FRESH 训练辅助检索器；执行模型冻结与全系统完全无训练是不同命题。
7. RHO 优化过程不读取外部评分，最终报告仍依赖独立 grader；多个回答一致不等于正确。
8. 同一冻结框架重复测试与多次独立框架优化是两类不确定性，统计报告应分开。

## 6. 用来检验结论的补充阅读

这两篇以实证比较为主，没有在本目录作为改进算法另写详解：

- [Finding the Right Fit: Model-Harness Interactions across Agent Tasks](https://arxiv.org/abs/2610.00917)：模型、任务与框架的搭配会改变排名，提醒我们不能只固定一种组合就宣称通用优势。
- [What Does a Harness Buy? Tokens, Mostly](https://arxiv.org/abs/2610.04433)：其编码实验中一些质量差异与重复执行噪声相当，成本差异更清晰。不能由此概括所有框架改进无效，但应认真控制调用预算与运行随机性。

当前项目自己的证据也应保留边界：[v3 结果](../../../reports/continuous_adaptation_v3/FINAL_SUMMARY.md)的两个 seed 方向不一致，[机制诊断](../../../reports/cam_v3r1_runtime_diagnostics/DIAGNOSIS.md)记录了预算来源及辅助生成限制。因此，本目录为新方向提供方法依据，不把旧结果当作任何新方法的性能证明。

## 7. 阅读每篇时可以带着的问题

- 优化器能改的是文字、图、组件，还是整个程序？哪些接口保持固定？
- 它获得了哪些执行证据，哪些是模型推断，哪些可以客观验证？
- 接受或选择候选使用哪组数据，有没有另一个完全隔离的最终评价？
- 求解阶段实际多了哪些调用、工具或检查？优化开销和部署开销是否分开？
- 论文证明了哪些组合有效，换成现有 GLM/Qwen 后还缺哪项证据？
- 若移植到当前仓库，收益究竟来自更好策略、更强模型，还是更多尝试？

读完后再比较重构方向，可以把选择建立在具体机制与依赖上，而不是依据论文标题或单个提升数字。
