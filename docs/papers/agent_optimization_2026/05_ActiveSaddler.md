# ActiveSaddler：让训练任务选择与 Agent 框架一起演化

> 原文：*ActiveSaddler: Automated Curriculum Learning for Agent Harness Optimization*。首次提交：2026-10-01；本文依据 v1，核对日期：2026-10-21。本文为方法解读，没有运行作者实现。
>
> [论文页面](https://arxiv.org/abs/2610.00906) · [正文与附录](https://arxiv.org/html/2610.00906v1) · [阅读索引](README.md)

## 1. 它把哪个固定环节变成了优化对象

许多方法研究怎样修改框架，却固定产生修改证据的训练任务顺序。框架改善后，原来有用的任务可能已没有信息量；某个弱点也可能值得集中修复多次。

ActiveSaddler 将**下一轮收集什么训练证据**作为随框架状态变化的决策。它以已有 harness optimizer 为基础增加课程层，主要实验接在 AutoSaddler 上，而不是自己重新发明一套框架修改器。[原文 §3—4](https://arxiv.org/html/2610.00906v1#S4)

这里的课程针对训练场景，不等于候选提出后再挑验证题。训练、development 和最终 test 的用途需要继续分开。

## 2. 为什么以失败模式作为 arm

若每个任务是一条 arm，相关失败难以共享经验；若只按“表格”“检索”等大类别分组，又可能把不同弱点混在一起。论文把可复用的失败模式作为动态 arm。

每条 arm 保存描述、支持它的训练场景集合，以及观察到它的框架版本、轨迹和诊断。新失败可以归入旧模式、组合已有模式，或实例化新模式。

提取分两步：先独立描述当前失败症状，再对照现有 registry 归一化。这样降低为了匹配旧分类而忽略新现象的风险。[原文 §4：Failure-Pattern Extraction](https://arxiv.org/html/2610.00906v1#S4)

重要边界是：arm 描述来自诊断，它是对可干预弱点的估计，并不天然等同于已经验证的根因。

## 3. 三个核心组件怎样协同

| 组件 | 输入 | 输出及作用 |
|---|---|---|
| Failure-Pattern Extractor | 修改前后失败与诊断证据 | 更新模式及其支持场景 |
| Arm Prioritizer | 当前框架与历次优化记录 | 估计已知模式的继续优化价值 |
| Exploration Controller | 已知模式、未见任务池和历史 | 决定探索未见场景，还是重访已知模式 |

一轮先决定 Draw/Pull：Draw 抽取未见训练任务；Pull 选择一个已知模式，再从其支持场景构造 batch。之后仍由底层优化器执行诊断、提出修改并用 development 数据选择版本。[原文 §4、附录 B](https://arxiv.org/html/2610.00906v1#S4)

```text
读取当前框架、模式注册表、未见场景池和历史
决定：探索新场景 / 重访旧模式
构造本轮训练 batch，执行并优化框架
从修改前后失败中提取和更新模式
更新历史，继续下一轮
```

以上为教学性概括。它优化的是反馈来源的分配，而不仅是失败题采样权重。

## 4. 优先级不是简单的失败频次

论文用 LLM 估计每个模式的 learning-progress score，考虑四个维度：是否仍活跃、能否通过框架修好、修好后覆盖面多大，以及产生副作用的风险。

随后通过 softmax 将分数转成概率，随机选择模式。温度影响偏向最高分还是保留更多探索。评分随最新框架与历史重算，不把很久以前的价值永久固定。[原文 §4：Arm Prioritization](https://arxiv.org/html/2610.00906v1#S4)

虽然论文采用非平稳 bandit 的问题表述，其主实现并不是经典 LinUCB/UCB 更新公式。不能把它与 MESH 的线性代理混为一谈。

## 5. 探索、遗忘与成功任务

持续重访已知失败，可能错过尚未发现的弱点。反过来，一直探索也可能让值得修复的问题得不到足够机会。Exploration Controller 根据当前优化状态决定二者取舍。

当所有训练场景已探索且各 arm 随后都访问过，曾成功但没有形成 arm 的任务可重新获得探索资格。如果现在失败，就能重新发现回归，而不必每改一次框架都完整重跑所有成功任务。[原文 §4：Exploration Control](https://arxiv.org/html/2610.00906v1#S4)

这是一种成本控制策略，并非对不遗忘的保证。任务重新纳入资格与当前弱点是否被准确识别，仍会影响效果。

## 6. 原实验究竟证明了什么

GAIA2 中，AutoSaddler 固定顺序的 test Pass@1 为 55.4%，ActiveSaddler 为 59.8%；Terminal-Bench 2.0 为 72.5%→80.0%。它们对应 +4.4、+7.5 个百分点，并有模式 arm、优先级和探索组件的消融。[原文 §5、表 1](https://arxiv.org/html/2610.00906v1#S5)

默认任务与优化模型为 gpt-5.5，推理设置不同。主表报告三个 test-time executions 的均值与标准差，并非三个独立优化训练种子；附录另有独立优化运行及替换底层优化器的检查。复现时必须区分这两层随机性。

## 7. 对当前连续适应实验的具体意义

**以下为本文构造的例子。** 当前固定 Cell/Sheet 交替，会把任务类型直接当课程结构。但同为 Cell 任务，可能分别存在多行表头误读、范围边界错位、公式结果未验证等问题；同一个范围问题也可能同时出现在 Sheet 任务。

新的模式注册表应绑定具体训练 ID 和发生时的框架版本。若“公式保存后未验证”已经修好，下一轮可以转向更有收益的模式；若某模式总因模型数学能力不足而失败，课程层应允许降低其优先级。

这与 CAM 的编辑预算不同：预算回答“改多少”，课程回答“收集哪些证据、先解决哪个问题”。两者不应共用一个含糊的失败置信度指标。

## 8. 内网实现与必要对照

**项目适配建议：** GLM 负责抽取、归一化与价值估计，注册表和概率采样在本地完成，Qwen 运行训练任务。只需要推理 API，但多轮分类与评分也会增加优化器开销。

可用固定顺序、随机顺序、按失败次数排序、规则式优先级与 LLM 动态课程做比较。保持底层提案器和评估规则一致，才能归因于课程。

尤其要记录重复访问次数、发现新模式数、实际训练 rollout 数、提案 token 和墙钟时间。课程可以主动挑信息量高的训练题，但最终评价必须覆盖预定分布，否则只会测出对被挑选场景的适应。

对整体重构最有价值的启示，是把“证据收集策略”纳入闭环，而不是只扩大更新算子的复杂度。

## 9. 非平稳性来自哪里

传统固定任务列表默认样本价值相对稳定，但框架优化会直接改变失败分布。某类问题修复后，再执行相同案例可能只得到重复成功；一个新检查器也可能暴露原来没有机会观察的下游错误。

因此，同一条 arm 的价值随框架版本变化，而 arm 集合本身也不断变化。过去失败很多不等于现在值得继续修，过去成功也不等于现在仍然成功。这种非平稳性使简单累计失败次数存在明显滞后。

论文的 learning progress 是对下一次优化机会可能带来的改善的估计，不是当前错误数量。一个常见但几乎无法通过框架解决的问题，可能比一个较少见、却能通过小修改广泛修复的问题更不值得投入。[原文 §4](https://arxiv.org/html/2610.00906v1#S4)

这也解释了课程与底层优化器的分工：课程决定“在哪些案例上产生证据”，优化器决定“如何利用证据修改程序”。底层优化器没有能力修复某类错误时，课程再准确也无法凭空产生解决能力。

## 10. 模式注册表不是只有标签的一张表

附录中的 registry 保存模式描述及其绑定的框架、轨迹、场景记录，还保存根因证据、活跃度、历史优化尝试和分数。其目的在于让模型判断某模式在当前框架下是否仍值得处理。

只保留“公式错误：出现 20 次”会丢失关键差异：这些错误来自哪个旧版本？是否已经有修复？修复后是否再次运行？最近一次失败是否是同一个机制？没有这些信息，优先级估计容易被陈旧统计误导。

论文采用按需访问的 pattern CLI，而不是把不断增长的注册表全部注入提示。不同会话获得不同操作能力，读模式、标记证据、评分和决定探索各有明确职责。[原文附录 A](https://arxiv.org/html/2610.00906v1)

**项目适配建议：** 模式记录至少包含稳定 ID、描述、支持任务、证据版本、最近观察、已尝试修改、当前状态和评分理由。模式重命名不应改变 ID；两个模式合并时需要保留来源映射，否则历史会看似消失。

## 11. 独立抽取与归一化为什么要分开

假设注册表已有“写入范围错误”，新失败发生在“保存后公式变成静态值”。如果抽取器一开始就被要求只能选择旧标签，可能把新现象归入范围错误，后续便会反复调整行列边界而没有触及公式保存过程。

先独立描述观察到的症状，再判断它能否归入已有模式，有助于发现新弱点。归一化又防止“范围越界”“写错区域”“行号偏移”被无意义地拆成大量近义 arm。

同一个任务可以关联多个模式，但这不表示各模式已经有独立因果贡献。选中其中一个模式，只是在该组案例上收集新证据；实际修复可能同时影响多个标签。应记录共现，而不是强迫每条轨迹只有一个原因。

**项目适配建议：** 将模型诊断和客观事件分开字段保存，例如“观察到目标范围遗漏”为事实，“因为模型没有理解表头”为推断。若后续证据推翻推断，不应改写原始轨迹。

## 12. 优先级打分与概率选择的具体含义

对当前各模式，LLM 结合严重性、可修复性、广泛性和副作用估计一个分数 φ。原方法再用 softmax 形成选择概率：

```text
q(a) = exp(φ(a)/τ) / Σ exp(φ(a')/τ)
下一条模式 a 从 q 中采样
```

τ 较小时更偏向高分模式，较大时更分散。保留随机性可以让较低优先级模式仍有被重新观察的机会，但这并不保证在有限预算内访问所有模式。

这些分数是模型评估，不是带严格校准置信度的统计收益预测。应保存评分依据，并检查排序能否预测后续实际改善。如果高分模式反复没有有效修改，而低分模式偶尔容易修复，说明估计需要重新审视。

也不能把四维因素直接自行相乘后说成原论文公式；主文将其作为 LLM 联合估计考虑的维度。规则聚合可以作为便宜的比较臂，但需要单独命名。

## 13. Draw/Pull 一轮推演

**下面是教学场景，不是原实验轨迹。** 初始还有大量未见训练题，已知模式只有“未保存文件”。控制器选择 Draw，新 batch 暴露“公式丢失”和“范围越界”。提取器将两者注册并绑定实际任务。

下一轮它认为公式问题有明确检查入口，于是 Pull 该模式，底层优化器增加保存后检查。验证改善后，registry 记录这次修改和当前版本。再次 Pull 时如果支持任务全部通过，也应记为“已访问且当前全通过”，不能把它伪装成一次产生改善的补丁。

此后控制器可以 Draw 寻找新问题，也可以重新检查范围越界。若一直 Pull 已修模式，会浪费训练执行；若一直 Draw，则已有高价值修复可能长期得不到机会。

当全部场景已探索、各 arm 随后都访问过，旧成功任务才按论文规则重新具备探索资格。如果这时重新失败，新的证据可以生成或激活相关 arm。这是发现回归的机会，不是对所有成功行为的持续完整监控。

## 14. 课程选择怎样污染评价，以及如何避免

主动课程会改变训练样本频率，所以训练集平均正确率不再是一个简单可比指标。某方法专挑难题，训练分可能更低，最终框架却更好；另一方法反复跑简单题，训练分很高，却没解决关键弱点。

应把课程效果放在预定 development 与最终 test 分布上评价，另报训练模式覆盖及执行量。不能让课程同时挑训练题、验证题和最终报告的题目，否则会把选择偏差误作方法收益。

使用底层优化器时，也要保持候选生成与验证规则一致。如果 ActiveSaddler 臂允许更多补丁或更强提案模型，无法把差异归给课程。原论文主张的重要比较是同一优化器下改变场景顺序与分配方式，而非把全部框架差异混在一起。

**项目适配建议：** 把采样决策独立保存为事件：当时有哪些可选模式，为什么选中它，抽了哪些任务，消耗多少 rollout，生成了什么候选，后续表现如何。这样才能回放课程本身，而不必再次请求模型。

## 15. 内网实现中真正困难的部分

本地维护集合和概率采样并不难，难点在于使模式语义与版本状态一致。GLM 可能将同一问题反复命名，也可能在新的框架下沿用旧判断；应该通过原始证据定位、模式规范化和显式版本关联减轻这种偏差。

另一个难点是场景支持量不均衡。有的模式只绑定一题，反复 Pull 会过拟合；有的模式覆盖很多题，但每轮预算有限。批次构造需要说明是否随机、是否重复、是否覆盖不同子情形，并记录真实支持 ID，而不是只使用模型自报“广泛存在”。

成本也不只有执行器。每轮抽取、归一化、评分、探索决策都可能产生额外 GLM 请求。内网免费并不消除吞吐和时间限制，应同时报告控制层开销与少跑了多少无效任务。

## 16. 哪些现象表明课程机制没有发挥作用

如果模式很多却只有少数被访问，先查分数分布与采样温度；如果不断创建近义模式，先查归一化；如果已修复问题长期占优，先查活跃状态和历史是否被读入；如果没有发现新弱点，先查控制器是否过度重访旧模式。

还应比较“高优先级”与“实际带来独立验证改善”的相关性。相关性弱不意味着课程完全无效，但说明模型对学习价值的估计可能没有优于便宜规则。此时按失败持续性或近期修复效果排序的对照尤其有价值。

该方法值得研究的地方，是让任务证据随框架状态而变化；是否需要复杂 LLM 控制，则取决于它比固定或规则课程节省了多少真实优化成本。
