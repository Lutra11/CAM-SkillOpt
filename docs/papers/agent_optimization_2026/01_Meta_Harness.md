# Meta-Harness：把 Agent 执行框架本身变成可优化程序

> 原文：*Meta-Harness: End-to-End Optimization of Model Harnesses*。首次提交：2026-03-30；本文依据 arXiv v1，核对日期：2026-10-21。本文为中文方法解读，没有运行作者实现。
>
> [论文页面](https://arxiv.org/abs/2603.28052) · [正文与附录](https://arxiv.org/html/2603.28052v1) · [阅读索引](README.md)

## 1. 先理解它究竟改进什么

Meta-Harness 把模型外面的执行程序作为搜索对象。这个程序决定模型看到哪些材料、如何检索历史、怎样组织提示词、如何更新状态以及如何串联调用。模型权重不变，但运行模型的方法可以改变。

它关心的瓶颈是：优化器拿到一个总分或一小段失败总结，往往无法发现真正有用的框架修改。导致失败的证据可能分散在旧版本代码、较早的工具输出和几个不同任务的轨迹里。因此，论文同时扩大了**修改空间**和**反馈访问空间**。[原文 §3](https://arxiv.org/html/2603.28052v1#S3)

相较 CAM-SkillOpt，变化发生在三个层次：

| 层次 | CAM-SkillOpt 当前主要方式 | Meta-Harness 的思路 |
|---|---|---|
| 优化产物 | 技能 Markdown 与其编辑 | 可执行的 harness 程序 |
| 证据输入 | 反思、合并后的修改建议及记忆上下文 | 可按需检索的历代代码、评分、原始轨迹 |
| 修改决策 | 固定 Reflect/Aggregate/Select/Update 阶段 | 提案 Agent 自行决定读什么、诊断什么、如何改程序 |

## 2. 最关键的机制：历史工件文件系统

每个被评估的框架都保存为一组文件，包含实现、得分和执行过程。提案器通过文件读取、搜索等开发工具访问这些材料，选择性地检查相关失败。

这里的“完整历史”指完整材料可供访问，**并不表示每轮把全部日志塞进上下文**。材料可以远大于上下文窗口，提案器需要主动检索。它也不必只继承当前最高分版本，可以参考不同旧版本的优缺点。[原文 §3、附录 A](https://arxiv.org/html/2603.28052v1#S3)

这会保留一种在逐级摘要中容易丢失的信息：某项行为在哪个版本引入、它解决了什么、又破坏了什么。模型可以据此提出更具体的代码修改假设，但这种解释仍须由执行评估检验，不能自动视为因果证明。

## 3. 整个优化循环如何运行

下面是教学性概括，不是作者代码：

```text
评估初始框架，保存源码、轨迹和评分
重复若干轮：
    提案 Agent 检索历史版本及相关执行记录
    提出一个或多个新框架程序
    检查程序是否符合运行接口
    在搜索任务上运行有效候选
    将新程序、结果和轨迹加入历史目录
根据搜索阶段的预定标准选择框架
在隔离的测试任务上评价
```

论文实验中的候选通常是单文件 Python 程序；提案器采用 Claude Code / Opus-4.6。它因此依赖的不只是一次文本补全，而是能检索文件、修改代码、检查接口的 coding-agent 能力。执行模型随任务域变化且保持冻结。

论文也维护候选集合与 Pareto 前沿，在涉及质量和上下文开销时报告权衡。因此，把它概括成“所有情况下只维护一个最高分框架”是不准确的；固定父代选择规则也不是其核心要求。[原文 §3](https://arxiv.org/html/2603.28052v1#S3)

## 4. 为什么可能比技能编辑有效

技能中的“多查一些相关案例”是一条建议；框架程序中的检索函数则可以决定查询如何构造、取哪些案例、怎样去重、结果过长时如何处理。后者直接改变模型收到的信息。

同样，技能可以要求“注意检查答案”，程序则能安排草稿后的一次验证调用，并根据结果决定是否修复。这类改变可以重组算法步骤，影响不局限于措辞。

代价也随之扩大：提案器可能生成不能运行的代码、引入不必要的调用，或搜索出依赖某个任务集合的规则。代码空间更强，并不等于搜索更省或泛化自动更好。

## 5. 论文证据应怎样读

在线分类实验的三数据集平均准确率为 48.6，ACE 对照为 40.9；额外上下文约为 11.4k 与 50.8k token。这支持其特定设置中质量与上下文效率同时改善，而非证明任意 Agent 都能获得同样幅度的收益。[原文 §4.1、表 2](https://arxiv.org/html/2603.28052v1#S4.SS1)

论文还评价检索增强数学推理和终端任务。不同任务使用不同实现、模型与指标，不能把它们拼成一个统一“框架提升率”。历史访问、提案器能力和候选初始状态也共同影响结果。

## 6. 用 SpreadsheetBench 解释一次可能的修改

**以下为本文构造的例子，不是作者报告的发现。**

假设几个失败任务都出现了表头识别错误。当前技能写着“识别表头后操作”，但执行器只收到首行预览；数据实际包含说明行、多行标题或合并区域。

按 Meta-Harness 的思路，提案器应该检查任务预览构造代码、失败文件的可见结构、旧版本的输入与输出，而不是直接再写一条表头建议。一个候选框架可以改变预览算法：显示多个候选表头区域、非空分布及合并单元格，再生成代码。

这个例子改变的是执行器的观察条件。若要证明它有效，应比较同一任务集上的旧预览和新预览，并记录新增输入量，而非同时更换模型、增加修复轮数。

## 7. 在内网环境如何借鉴

**下列为项目适配建议，不是论文原配置。**

- 用 GLM 作为提案器、Qwen 作为固定执行器；这属于跨模型优化变体，原论文的闭源提案能力不能直接继承。
- 复用现有的预测目录、conversation、usage 和源码冻结记录，建立按候选版本索引的工件目录。
- 初期开放输入预览、上下文拼接、输出解析、检查与恢复等少数可编辑入口，先测 GLM 是否能稳定生成有效程序。
- 保持数据划分、评分器与模型调用记录由外部实验驱动器管理。候选优化的是执行过程，评价标准需要固定。

建议的最小判别实验是：同一个 GLM、同一代码修改范围、同等评估预算下，对比“只给摘要”与“可访问历史原始工件”。这样才能回答本文最有价值的主张是否在内网成立。

## 8. 对框架重构的启示与边界

最值得迁移的是**程序级候选表示＋可检索的历史证据**。现有 Trainer 可以继续承担实验调度，但其更新对象需要从 `skill_content` 扩展为有版本、接口和运行记录的框架。

需要保留的判断边界是：作者展示的是强 coding agent 驱动的框架搜索；“用 GLM 改程序”具有工程可行性，但质量和开销尚待验证。自由修改整个仓库也不是复现该思想的必要起点。

精读时优先看 §3 的反馈访问方式，再看附录 A 的提案行为，最后看附录 B 的具体发现。阅读问题应是“它实际改变了哪条信息或执行路径”，而不只是“最终增加了哪些提示词”。

## 9. 将目标写清楚：搜索的是程序，而不是某道题的答案

用 M 表示冻结执行模型，用 H 表示框架，用 x 表示任务。一次执行产生轨迹 τ，外部评价给出奖励 R。论文的目标可写成：

```text
H* = argmax_H E[R(x, τ)]，其中 τ 来自 Run(M, H, x)
```

这里 H 可以改变模型输入和执行组织，所以即使 M 完全不变，同一个 x 的轨迹分布也会改变。优化的结果应能应用到未来同分布任务，而不是只保存某道训练题的答案。

需要区分三个角色：执行模型解决当前任务，提案 Agent 修改框架，外部实验驱动器运行评价并保存工件。提案 Agent 可以研究评分与轨迹，但评分器本身不应成为可自由改写的候选内容。否则分数变化可能来自评价口径变化，无法解释为 Agent 改善。

原文外层循环比较简洁，是把复杂诊断交给提案 Agent，而不是消除了诊断。若换成只会返回一段文本、没有读文件和检查程序能力的调用，实际已经删掉了方法的重要部分。[原文 §3、附录 D](https://arxiv.org/html/2603.28052v1)

## 10. 一个有用的历史目录必须能回答哪些问题

**以下是项目实现建议，不是作者规定的目录格式。** 历史工件至少应支持从“版本为何变好”一路追到“具体输入和行为怎样变了”：

| 工件 | 应保留的信息 | 支持的诊断问题 |
|---|---|---|
| 候选源码 | 内容哈希、接口版本、直接父代 | 当前执行的究竟是哪份程序 |
| 修改说明 | 修改意图、目标失败、预期副作用 | 哪个假设正在被检验 |
| 逐任务结果 | 任务 ID、完成状态、客观得分 | 总分变化由哪些任务贡献 |
| 模型事件 | 实际请求、响应、工具观察、调用角色 | 模型是否真的看到新增证据 |
| 产物与异常 | 输出位置、检查信息、错误阶段 | 是语义错误还是执行失败 |
| 资源记录 | token、调用次数、耗时、重试 | 提升是否靠额外尝试换来 |

只有一个 `summary.json` 不能替代这组材料。总分相同的两个版本，也可能在完全不同的任务上成功；提案器应能查出“谁赢了谁、为什么可能赢”，而不是只看到一个均值。

更细的改进是提供只读查询入口：列出候选、筛选某类错误、对比两个版本在同一道题上的事件、定位首次行为分叉。原文附录 D 也讨论了可查询日志和小型 CLI 的工程价值，但这些是经验建议，不能当作已经被单独消融证明的结论。

## 11. 完整推演：从观察不足到一个可检验的候选

**本节为教学性假设场景，所有版本和结果均为示意。** 设 H0 的表格预览总是取前几行；失败组中，多份工作簿前面有说明文字，模型把说明当成字段名。

第一步，提案器从失败记录查到 H0 的真实输入，再查看成功题是否也有类似格式。如果只有一题异常，可能只是个案；若多题都因为前置说明行而误判，则形成一个可复用的观察假设。

第二步，提案器检查旧版本 H1。H1 曾加长预览，部分题改善，却因输入过长而增加截断。于是新候选 H2 可以改成“按非空块提供区域摘要”，而不是机械地显示更多行。这正体现跨版本历史的作用：继承旧想法的有效部分，同时避开已有副作用。

第三步，H2 做接口和小样例检查。确认它在空表、多个 sheet、合并区域下都能返回约定输入，并且没有读取任何 gold 文件。能运行只是准入条件，尚未给出性能结论。

第四步，在搜索任务上比较 H2 与参照版本。分析新增成功题、丢失成功题、输入增长和超时。如果总分只略升但输入翻倍，就需要依据预定目标决定是否保留；不能等看到结果后临时改变“最好”的定义。

第五步，将成功、失败和拒绝候选都写回历史。即使 H2 被拒绝，后续提案仍可以利用“非空块摘要曾在哪些格式下失效”的证据。历史价值不只来自胜者，也来自减少重复试错。

## 12. 如何分辨“程序搜索有效”和“强提案模型有效”

这篇方法包含多个可能来源，必须逐个对照。以下为建议实验，而非作者已完成的内网结果。

| 比较 | 两臂共同固定 | 唯一重点变化 |
|---|---|---|
| 摘要反馈 vs 原始工件访问 | 提案器、修改接口、预算 | 反馈的信息访问方式 |
| 一次性候选 vs 迭代历史搜索 | 同一提案模型、总候选数 | 是否利用旧结果继续调整 |
| 技能编辑 vs 程序编辑 | 执行模型、任务、评价规则 | 可修改对象的表达能力 |
| GLM 提案 vs 较弱模型提案 | 工具与反馈完全一致 | 提案器能力 |

如果同时换成 GLM、开放代码修改、增加候选数并扩大上下文，结果即使变好，也无法知道哪个变化关键。优先做其中一条干净比较，比一次堆叠整套机制更有解释力。

还要测量提案器究竟使用了哪些文件。拥有读取权限不等于访问过原始证据；若它每次只读取最终分数，那么“完整历史机制被实际使用”的证据仍然不足。可以记录文件访问次数、跨版本引用、诊断引用的任务 ID，以及修改与证据是否对应。

## 13. 在当前代码结构中怎样形成最小实现

**以下是适配说明，不是已经执行的重构方案。** 可以保留现有数据加载和评分路径，把一次执行所需的观察构造、提示组装、生成、检查及恢复包装为一个有版本的候选程序。Trainer 调用候选入口获得轨迹，而不再只传递 `skill_content`。

提案器使用单独工作目录，拿到当前候选、历史索引和可编辑接口说明。它返回实际文件及修改说明；外部驱动器计算源码哈希、做检查、启动任务并归档。这样能够把“模型说已修改”和“真正执行的字节已改变”对应起来。

初期只开放少数入口，仍能检验原思想。全程序自由改写提高搜索空间，同时大幅增加有效性问题；它应在局部入口已经稳定后再作为可比较的扩展。任何生成失败、无改动、检查失败、任务级失败都应该记录为不同阶段，而不是一律赋零后继续优化。

## 14. 读到怎样的证据，才值得继续扩大规模

第一，GLM 能持续产生符合接口且有实际行为差异的程序。第二，提案引用的历史案例确实与改动相关。第三，在固定执行模型与预算下，候选能改善独立验证表现，而不只是搜索题复现。第四，重复搜索产生的收益方向相对一致。

如果大量成本花在语法修复和接口恢复，瓶颈是提案工程能力；如果程序有效但没有效果，可能是修改面不合适或失败诊断无效；如果搜索集改善而新题退化，则需要检查硬编码、验证适应和任务分布偏差。不同现象应触发不同修正，不能统一归结为“再给更多历史”。

对本项目而言，Meta-Harness 最值得保留的研究判断是：执行程序和可检索证据可以共同成为学习载体。它是否优于现有文本更新，需要由这些过程指标和最终任务表现共同回答。

## 15. 为什么提案器的说明文档仍然重要

框架优化超出技能编辑，并不意味着提案器不再需要清楚的任务说明。原文附录 D 将这份说明视为引导搜索的重要工程杠杆：应告诉模型目录如何组织、候选写到哪里、如何查询历史、哪些入口和评价设施不能改，以及必须交付哪些工件。

需要谨慎的是约束与自由度的平衡。说明过于宽泛，提案器会浪费时间导航和猜测接口；说明把诊断步骤规定得太死，又可能丢掉主动检索历史的价值。更合理的边界是固定运行协议与产物要求，允许模型自主选择需要调查的证据及修改假设。

**项目适配建议：** 正式比较前，用少量离线样例或短搜索检查提案器能否找到相关文件、生成合法候选和正确引用任务。这个阶段用于校准工作流；其结果不应混入后续冻结协议下的正式性能比较。
