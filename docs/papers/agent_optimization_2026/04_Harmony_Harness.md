# Harmony Harness：多目标、分解式的 Agent 框架演化

> 原文：*Harmony Harness: Multi-Objective Self-Evolution of Agent Harnesses*。首次提交：2026-10-10；本文依据 v1，核对日期：2026-10-21。本文为方法解读，没有运行作者实现。
>
> [论文页面](https://arxiv.org/abs/2610.15150) · [正文与附录](https://arxiv.org/html/2610.15150v1) · [阅读索引](README.md)

## 1. 它提出了什么改进

Harmony Harness 同时处理两类问题：框架优化可能只提升某个目标而损害另一个目标；在单个环境上形成的改进可能无法迁移。

它将整个框架视为演化对象，用多目标分解搜索维护不同取舍的候选；同时按组件类型和适配范围组织修改，再按任务动态组合。[原文 §3—4](https://arxiv.org/html/2610.15150v1#S4)

**原论文实验的两个目标是功能性和安全性，不能直接改述为准确率和 token 成本。** 后者可以成为本项目的适配目标，但属于新的实验设置。

## 2. 为什么不能只看一个总分

论文分别衡量功能成功 F 与安全成功 S，主要报告同一次轨迹同时满足二者的比例，即 secure-pass。两个边际得分相同的框架，可能在不同任务上分别成功，因而联合成功率不同。

搜索使用两个边际目标，是为了提供更明确的失败信息；最终仍检查联合指标。不能只看到两项平均数都高，就推断每道题同时满足要求。[原文 §3](https://arxiv.org/html/2610.15150v1#S3)

部署时需要选一个框架。原文依据搜索集上两项目标较低者的得分选取最均衡子代，不利用 held-out 数据挑选最终版本。

## 3. MOEA/D 怎样维护不同取舍

论文设置多组偏好权重，每组对应一个子问题和一个当前框架。某些子问题更看重功能，另一些更看重安全。

它用加权 Tchebycheff 标量化衡量候选与当前理想点的差距：重点关注当前偏离目标最严重的加权维度。一个新框架可以替换附近偏好中更差的框架，但不会强迫所有偏好都只保留同一个胜者。原设置限制一个子代最多替换两个邻近 incumbent。[原文 §4.1](https://arxiv.org/html/2610.15150v1#S4.SS1)

这不同于全程使用一组固定权重将所有目标加成单一分数。维护不同选择压力可以保留不同取舍，但**不自动保证行为多样性**：多个代码不同的框架仍可能执行相同策略。

## 4. 分解式演化：改什么，以及改动归哪里

组件类型分为 tools、skills、logic，logic 包含提示、验证、控制流和编排。另一维是 general 与 environment-specific，即通用机制和环境特定实现。

提案过程先诊断执行反馈、形成修改假设，再选择组件与范围。通用和特定不是模型根据语义给出的抽象标签，而是有明确存放、加载规则的运行组织方式。另有 generalize 操作调整边界，将过度特化的实现重新组织。[原文 §4.2、附录 E](https://arxiv.org/html/2610.15150v1#S4.SS2)

| 修改问题 | 可能的组件类型 | 适配范围需要判断什么 |
|---|---|---|
| 调用错误后怎样整理反馈 | logic / tools | 能否适用于其他工具环境 |
| 某类任务的专门求解过程 | skills | 是否依赖当前任务域的约定 |
| 特定构建系统的检查命令 | tools | 依赖是否只存在于当前环境 |

表中是解释性分类，不是作者固定的自动归类规则。

## 5. 动态组合怎样发生

运行时先加载通用组件与当前环境组件。组合 Agent 读取任务和已注册步骤，构造任务相关 DAG，执行器检查后按依赖运行。组合器选择已有组件，不在推理阶段重新修改其实现。

跨到未演化过的环境时，源环境的专门组件不会直接加载；通用部分才是主要迁移载体。[原文 §4.3、附录 F](https://arxiv.org/html/2610.15150v1#S4.SS3)

```text
演化阶段：反馈 → 修改假设 → 组件/范围选择 → 新框架 → 验证 → 多目标替换
求解阶段：环境与任务 → 加载组件池 → 生成执行 DAG → 检查并运行
```

这段流程为教学性概括。它要求可靠的步骤注册、DAG 校验与状态传递，不能只通过提示“请动态组合”完成。

## 6. 候选程序怎样避免无效运行

附录给出三层检查：导入与接口；使用 stub 模型的离线执行及自测；静态完整性。最后一层还检查父代测试断言是否保留、调用与函数签名是否匹配。

失败诊断返回提案器一次修复机会；再次失败则回滚。通过这些检查后，候选才进入真实任务评价。[原文附录 E.5](https://arxiv.org/html/2610.15150v1#A5.SS5)

要区分程序有效性与性能：通过 smoke test 只能说明基本运行协议成立，并不能证明候选更好。

## 7. 实验依据与局限

论文使用 SecRepoBench、BaxBench，分别划分 evolve、held-out-ID、held-out-OOD；每部分任务数分别为 30 和 28。主要设置中提案器和求解器均为 gemini-3.6-flash。指标是联合功能/安全成功，且分析了跨分布和跨基准迁移。[原文 §5](https://arxiv.org/html/2610.15150v1#S5)

样本相对有限，不能将某个分割上的大幅变化直接推成稳定普遍规律。还要注意：论文中的 Meta-Harness 对照是其特定演化设置，不能据此声称 Meta-Harness 原方法从未考虑多目标；后者原文也讨论 Pareto 权衡。

## 8. 用内网模型如何实现其思想

**以下为项目适配建议。** 在 SpreadsheetBench 上，可以把任务正确率、平均调用量/耗时作为可测量目标，并建立通用执行与表格特定观察/验证组件。GLM 负责离线提案及可选组合，Qwen 固定执行。

例如，“将 Python 异常整理成修复反馈”可能是通用逻辑；“检查合并单元格布局”是表格专门工具。能否迁移到 SearchQA，应通过仅加载通用部分的实验检验，而不是只看目录命名。

若新增每任务 GLM 组合调用，必须计入求解预算。还应与固定流程、固定权重搜索、无范围分解、无动态组合分别对照。改成质量—成本目标后，应称为借鉴 Harmony 的项目变体，不能沿用其功能—安全实验结论。

最值得借鉴的是“多种目标取舍＋明确适配范围＋运行时组合”共同定义整体框架；最需要克制的是同时引入全部复杂度，否则难以解释收益来自哪部分。

## 9. 用一个反例理解边际成功与联合成功

**以下为教学数字，不是论文实验。** 有十个任务，框架 A 在前五个任务功能成功、后五个任务安全成功；框架 B 在同五个任务上同时功能与安全成功。两者的功能率和安全率都为 50%，联合成功率却分别是 0% 与 50%。

所以，两个目标的均值提高只能描述边际变化，不能保证它们在同一次执行上同时成立。论文以功能性和安全性作为搜索信号，同时报告二者联合成功，正是为了暴露这种差异。

对本项目若改成“正确且在预算内”，也应测每个任务是否同时满足，而不只分别报告平均正确率和平均 token。一个方法可能让简单题极省、难题极贵，平均成本看起来合理，却不满足逐任务预算要求。这是类比推导，不是作者已做过的成本实验。[原文 §3](https://arxiv.org/html/2610.15150v1#S3)

## 10. 从固定加权和到分解式多目标搜索

单一加权和将每个框架压缩为一个分数，权重一旦固定，就只偏好某一种折中。Harmony 使用多个权重向量，每个子问题保留自己的 incumbent，并用 Tchebycheff 距离评估：

```text
g(H | λ, z*) = max_j λ_j × |z*_j − f_j(H)|
```

z* 是迄今观察到的理想点，f_j 是第 j 个目标的测量值，距离越小越好。这里的最大值让最差加权短板更突出：如果功能性很好、安全性很差，继续只提升功能通常不会改善这个短板。

每个子问题有相近偏好的邻居。通常从自身父代产生修改，停滞时也可以借鉴邻居；子代评价后按各邻居自己的偏好比较是否替换。替换有上限，从而避免一个新候选立即占满整个种群。[原文 §4.1](https://arxiv.org/html/2610.15150v1#S4.SS1)

这提供的是不同选择压力，而非理论上已经得到完整 Pareto 前沿。有限种群、有限评估和随机提案只能形成当前近似；若两个目标实际上高度一致，维持多个偏好也未必产生明显不同的行为。

## 11. 两维分解怎样控制修改范围

第一维按职责分 tools、skills、logic；第二维按适配范围分 general、environment-specific。两维交叉后，同一个错误可能有几种不同的修复位置。

例如工具参数格式经常错误，可以修改工具包装器以验证参数，也可以修改规划逻辑以提前读取参数约定。前者可能是通用工具机制，后者可能只适用于某个环境。提案器需要同时选择干预入口和存放范围。

这样做的动机并不是所有组件都能被唯一正确分类，而是使范围成为可见决策。一个训练环境里有效的规则如果被误放入通用区，就可能在迁移时被无条件带走；反之，普遍有用的异常处理若只放在特定区，又会限制复用。

generalize 操作重新组织这种边界，因此“通用”和“特定”不是一次命名后永久固定的事实。是否真正通用，最后仍需要跨环境运行，而不是根据模型解释或目录位置断言。[原文 §4.2、附录 E](https://arxiv.org/html/2610.15150v1#S4.SS2)

## 12. 一次子代怎样从诊断走到运行

**以下是按论文机制整理的教学流程。** 父代先产生任务反馈；提案器阅读功能失败、安全失败及部分执行证据，针对当前偏好形成一个修改假设。它据此选择工具、技能或逻辑入口，再决定在通用还是环境特定范围中实现。

生成的候选先做导入和接口检查，再用 stub 环境执行基本协议，最后做静态完整性检查。失败时只有有限修复机会，反复失败则恢复父代，不把不可运行程序送入昂贵任务评估。

通过准入后才产生客观目标值，并用于邻域替换。这里至少有三种状态：程序合法、被某个子问题保留、最终选为部署框架。合法不等于高分，某偏好保留也不等于在所有目标上支配其他版本。

本地实现时，必须把三类决定分别记录。若全部用同一个 `accept` 字段表达，就很难解释“候选检查通过但性能差”“候选进入种群但没被最终选择”等情况。

## 13. 任务级 DAG 的输入、校验与执行

组合 Agent 不是任意写一份新程序，而是从已注册组件与步骤中规划本次任务流程。其输出 DAG 应指明节点、依赖和条件，运行器再检查并执行。

**以下为项目示例，不是论文中的表格任务结果。** 简单数值修改可以选择“观察→生成→执行→检查”；带公式或样式的任务可能增加对应检查步骤；出现特定异常后再进入修复节点。任务不同，激活的步骤与工具也不同。

校验不只检查有没有环。还需要确认节点已注册、依赖结果类型匹配、条件可解释、必要输入存在，以及终止和预算可以落实。一个图结构上无环但引用不存在工具的计划，仍然不可执行。

原方法在推理时组合已有组件，不允许把“组合计划”当成未经验证的新组件代码。因此部署阶段的搜索空间仍受注册与加载机制约束。[原文 §4.3、附录 F](https://arxiv.org/html/2610.15150v1#S4.SS3)

## 14. 如何把迁移能力做成真正的实验证据

**项目适配建议：** 在一个任务域演化框架后，冻结通用部分，并在另一个域运行时不加载源域专用目录。比较初始通用框架、演化通用框架、以及允许额外新域适配的框架，分别回答零样本迁移和继续适配问题。

如果把源域技能、工具和特定格式假设全搬过去，再报告新域效果，测到的是整包迁移，不是范围分解的价值。若为了新域修改了通用代码，也不再是纯冻结迁移，需要另记版本和预算。

应报告通用组件实际调用了多少、哪些被任务组合器跳过、失败是否来自错误加载。否则新域提高可能只来自组合器本身更强，不能归因于学到了可迁移组件。

在已有 SearchQA 和 SpreadsheetBench 上，环境差异较大，通用的状态、错误和预算机制可能复用，领域观察工具未必复用。这个差异恰好可以检验范围组织，而不是强求所有模块共享。

## 15. 多目标实验最容易混淆的三个层次

第一层是目标定义：正确率、安全、延迟、成本各自如何测。第二层是搜索算法：固定加权和、约束式选择或 MOEA/D。第三层是最终部署选择：从搜索候选中挑哪一个版本。

不能在一条臂里用多权重探索、另一条只用某个不利权重，然后声称全部收益来自分解搜索。也不能看到测试集后挑最合适偏好再当成预先确定的最终模型。偏好和最终选择规则都应该在最终测试前固定。

需要的对照至少包括：相同目标下的单一标量搜索、只增加多目标种群、再加入范围分解，最后加入动态组合。各层使用相同评价设施并分别计量开销。这样才能知道收益是目标覆盖、组织方式还是推理时规划带来的。

Harmony 给整体框架设计的价值在于让“取舍、范围和运行组合”成为显式机制；它对当前项目是否划算，要由这些分层证据决定。

## 16. 哪些东西应该归入固定评价设施

**项目适配建议：** 数据划分、任务 ID、客观评分器和最终报告规则由框架外的实验驱动器管理；候选可以改求解工具和验证策略，但不应改决定研究分数的外部评价标准。

原因在于，框架内部的验证器是被优化行为，外部评分器是衡量这些行为是否有效的参照。内部检查变得更容易通过，不能自动使最终任务得分提高；只有产物满足外部规则，才构成真实改善。

原文的静态完整性和自测保留检查，也体现了不能让候选靠删除检查而显得更有效的工程问题。移植时应记录内部检查的实际触发与外部结果，才能区分更好执行和更宽松自评。
